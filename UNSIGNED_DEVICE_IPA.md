# Unsigned physical-iPhone IPA — preparation only

The existing Simulator workflow is unchanged. The user reports that its GitHub Actions build/tests pass. This independent device build creates an **unsigned iPhoneOS IPA**, intended to be re-signed locally and installed on the user's own iPhone. It does not run tests on an iPhone, enroll in the Apple Developer Program, or install anything.

## Run and download

1. Add `.github/workflows/ios-device-build.yml`, `Scripts/build-unsigned-device.sh`, `Scripts/verify_device_app.py`, and `Scripts/verify_device_ipa.py` to the existing repository, preserving the existing project and Simulator CI files. Commit and push the additions to the default branch. The source root remains the `FitPhotoSpike` folder.
2. In GitHub open the repository → **Actions** → **Unsigned iPhone IPA** → **Run workflow**. Choose the branch containing these files and click **Run workflow**. There are no inputs or secrets. A newly added manually dispatched workflow generally needs to be on the default branch before the button appears.
3. Wait for **Build and verify unsigned iPhoneOS IPA** to succeed. Open that run's summary and download the artifact named **FitPhotoSpike-unsigned-ipa**.
4. Extract GitHub's downloaded artifact ZIP on Windows. Locate **FitPhotoSpike-unsigned.ipa**, `FitPhotoSpike-unsigned.ipa.sha256`, and `device-build-verification.json` inside it; GitHub may preserve an `Artifacts` subfolder. The outer artifact ZIP is not the IPA. The IPA itself contains `Payload/FitPhotoSpike.app`.
5. Inspect the JSON report and the `executable-file`, `executable-architectures`, `executable-platform`, `device-verification`, and `ipa-verification` logs. The report must show passed verification, `arm64`, and the iOS device platform. Only then use the IPA with a local re-signing/install tool.

The supplied `FitPhotoSpike-device-workflow-additions.zip` contains only the four new workflow/helper files and this guide. Extract it into the existing repository root; it contains no replacement project, app sources, or Simulator workflow. This avoids overwriting any fixes already made in your passing GitHub repository.

With GitHub CLI already authenticated, from the existing repository folder:

```powershell
git add .github/workflows/ios-device-build.yml Scripts/build-unsigned-device.sh Scripts/verify_device_app.py Scripts/verify_device_ipa.py UNSIGNED_DEVICE_IPA.md
git commit -m 'Add separate unsigned iPhone device IPA workflow'
git push
gh workflow run ios-device-build.yml --ref main
gh run list --workflow ios-device-build.yml --limit 5
$runId = Read-Host 'Enter the unsigned device workflow run ID'
gh run watch $runId --exit-status
gh run download $runId --name FitPhotoSpike-unsigned-ipa --dir device-download
Get-ChildItem -LiteralPath device-download -Recurse -Filter FitPhotoSpike-unsigned.ipa
```

Substitute the actual default branch for `main` when different. Install/authenticate GitHub CLI using [WINDOWS_SETUP.md](WINDOWS_SETUP.md) if needed; do not initialize or create another repository when one already exists. After a failed build, inspect its separate **ios-device-build-diagnostics-RUNID-ATTEMPT** artifact. No IPA is uploaded if a verification step fails.

## What is verified by a successful run

The new workflow uses the same `macos-26` / Xcode 26.6 toolchain selection as the existing Simulator workflow, with its own dispatch and concurrency group. It invokes the existing project and shared scheme with:

```sh
xcodebuild build \
  -project FitPhotoSpike.xcodeproj -scheme FitPhotoSpike \
  -configuration Release -sdk iphoneos -destination 'generic/platform=iOS' \
  -derivedDataPath <run-directory>/DerivedData \
  CODE_SIGNING_ALLOWED=NO ARCHS=arm64
```

`CODE_SIGNING_ALLOWED=NO` disables the signing stage; the workflow does not add redundant signing identity/profile settings, export an archive, or change project build settings. No certificates, provisioning profiles, credentials, secrets, TestFlight, or App Store Connect are involved. It expects `Release-iphoneos/FitPhotoSpike.app`, never a Simulator build directory.

The script logs `file`, `lipo -archs`, and `vtool -show-build`. A Python checker validates the bundle's iPhoneOS platform and parses its Mach-O load commands: **arm64 plus the iOS device platform is required**. ARM64 Simulator binaries are explicitly rejected. The script also requires an unsigned code object and no embedded provisioning profile or bundle signature.

Generated App Intents metadata is required in the built app, including the **FitPhotosIntent / Fit Photos to 4:5** action. This validates build output, not a string found in a Swift source file. Missing, empty, unrecognized, or mismatched metadata fails the job with diagnostics rather than producing an apparently valid IPA. The metadata is generated by the normal Xcode build; no stub is injected. The check is tied to the selected Xcode metadata format, and an SDK format change may require updating the checker after inspecting the artifact.

The app is copied intact into `Payload/FitPhotoSpike.app`, zipped as `FitPhotoSpike-unsigned.ipa`, and checked for correct layout, executable permissions, ZIP integrity, and byte-for-byte correspondence with every verified application file, including its App Intents metadata. The download contains a SHA-256 and JSON verification report. Artifacts are retained for 14 days; GitHub account Actions usage limits still apply.

## Re-signing and Shortcuts discovery

An unsigned IPA cannot launch directly on a normal iPhone. Re-signing must produce a valid development signature and provisioning profile for your account/device. Windows tools such as Sideloadly document support for free Apple accounts; this workflow does not install, configure, or authenticate such a tool. Apple's Personal Team provisioning has limits and expires after seven days, so periodic re-signing/refresh can be required. See [Apple account limits](https://developer.apple.com/help/account/basics/about-your-developer-account) and the tool vendor's [Sideloadly documentation](https://sideloadly.io/).

Things to record or investigate if **Fit Photos to 4:5** does not appear:

- **Metadata preservation:** the re-signer must retain `Metadata.appintents` and normal app resources. Do not use options that strip metadata, replace the binary, inject tweaks, or otherwise alter the app. This project has no separate App Intents extension to remove.
- **Bundle identity and signing consistency:** preserve the bundle identifier when the signing tool permits it. If the tool changes it, record the original and installed identifiers, and make sure the final profile/application identifier/signature agree. Changing bundle identity may affect system registration or compiled metadata associations; that is a risk to test, not a proven failure for every tool. Apple documents signing consistency in [TN2415](https://developer.apple.com/library/archive/technotes/tn2415/_index.html).
- **Installation and trust:** complete the tool's legitimate installation/trust steps and enable Developer Mode if iOS requests it. Launch Fit Photos once, then create a fresh shortcut and search for the action under the installed app. An expired profile or an app that cannot launch is an installation/signing failure first.
- **System registration:** installation success and preserved metadata do not prove that iOS registered the action. Record the iOS build, tool/version, identifier changes, launch behavior, and exact Shortcuts error. A stale shortcut referencing a previous installation/identifier should be replaced with a newly selected action.

The app has no custom entitlement file and the workflow adds no Siri entitlement. There is no claim that a free account categorically prevents App Intents; there is also no guarantee that a particular third-party re-signer preserves discovery. The supported public AppIntent action remains in the existing application target. See Apple's [AppIntent overview](https://developer.apple.com/documentation/appintents/appintent).
